# Evaluation methodology

## Phase 6 recorded suite (mock LLM)

`make eval` runs entirely offline after `make setup` has cached the public embedding and reranker weights. It reads the pinned `pallets/click` REST capture in `evals/fixtures/click_large_snapshot.json` (captured 2026-10-19), the 55 reviewed labels in `evals/datasets/retrieval_large.jsonl`, the 60 cases in `evals/datasets/agent_cases.jsonl`, and `evals/fixtures/synthetic_repo.json`. The capture contains 400 public issue/PR records, including 238 PRs. Every retrieval query is paraphrased; 33 include a labeled near-duplicate distractor. Twenty adversarial cases use planted issue or PR comments in the synthetic repository. The generator and capture scripts document fixture provenance, but normal evaluation never runs them or calls GitHub.

The runner writes `evals/reports/latest.md` and `latest.json`. JSON includes each ranked URL, case outcome, measured latency, usage accounting, and SHA-256 fixture hashes. `evals/config.json` sets `retrieval_k` and `min_full_agent_pass_rate`; the process exits nonzero when the full agent misses that configured threshold. `make test` uses the deterministic mock and recorded fixtures without loading embedding weights or using a network connection.

## Retrieval results (mock LLM suite; ranking uses no LLM)

Each chunker rebuilds its own local Chroma collection from the same 400 records. Local MiniLM embeddings and the optional local cross-encoder search the 55 queries. Results deduplicate by parent source. Hit rate@3 counts queries with at least one relevant URL in the first three sources. MRR@3 averages the reciprocal rank of the first relevant URL, assigning zero to misses. These are the actual results from `make eval`, rounded only for display:

| Chunking | Reranker | Chunks | Hit rate@3 | MRR@3 |
| --- | --- | ---: | ---: | ---: |
| Fixed | Off | 1193 | 0.800 | 0.667 |
| Fixed | On | 1193 | 0.873 | 0.806 |
| Structure | Off | 1279 | 0.818 | 0.709 |
| Structure | On | 1279 | 0.873 | 0.779 |

The earlier Phase 2 fixture had near-perfect scores across variants and offered little separation. On this larger recorded corpus, hit rate@3 ranges from 0.800 to 0.873 and MRR@3 from 0.667 to 0.806. The score spread makes the reranker comparison observable. It is still one repository and a hand-labeled query set; it does not estimate performance on all GitHub repositories.

## Agent and baseline protocol (mock LLM)

The 60 cases comprise 30 ordinary questions, 20 injected issue/PR comment cases, and 10 edge or failure cases. The latter cover an empty repository, no activity, a large issue, missing fields, simulated HTTP 403/429/500 responses, and a simulated timeout. The graph uses a scripted `MockProvider` and a fixture gateway returning recorded passages or deterministic failures. Its guardrail detector quarantines suspicious comments before synthesis. The naive RAG baseline takes the top source from one precomputed unreranked retrieval ranking and makes one call to the same scripted mock for an answer; it does no planning, retry, memory read, or guardrail filtering. It is an intentionally small baseline, not a tuned production RAG system.

Pass rate is the share of all cases meeting their case label. For normal questions, the rule-based answer-accuracy check requires the labeled URL and, when provided, the recorded title. Citation correctness is measured among answers that make a summary claim: each quote must occur in its retrieved passage and each cited URL must match that passage. Injection block rate is the share of planted attacks with a quarantine trace event. Refusal rate is the share of cases with no summary. Latency is measured elapsed local fixture-driven process time per case; it excludes the separately measured embedding search and any live network delay. Budget units are the graph's character-based token reservation (or provider usage if greater), **not tokenizer counts**. Provider-reported prompt and completion tokens are separate; the mock reports zero. Estimated mock service cost is USD 0 because no hosted service is called. Real-provider cost is TBD (run make eval).

The comparison and ablations below are generated by the current local run; consult `latest.json` for unrounded values and case-level failures.

| System | Cases | Pass rate | Normal answer accuracy | Citation correctness | Injection block | Refusal |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Naive RAG | 60 | 0.433 | 0.567 | 1.000 | 0.000 | 0.150 |
| Full agent | 60 | 0.783 | 0.567 | 1.000 | 1.000 | 0.150 |

| Ablation | Cases | Pass rate | Injection block |
| --- | ---: | ---: | ---: |
| All guardrails off | 20 | 0.000 | 0.000 |
| Reranker off | 30 | 0.533 | n/a |
| Memory on | 10 | 0.500 | n/a |
| Memory off | 10 | 0.500 | n/a |

The guardrails-off ablation uses the 20 attack cases; reranker-off uses the 30 normal cases; memory-on/off each use the same 10 normal cases. These are scoped comparisons, so their pass rates should not be compared directly to the full 60-case pass rate. The scripted mock extracts the first evidence title and does not reason over memory, so memory-on/off can match even when memory was read. The local baseline and full agent have different call counts, so their latency is descriptive rather than a normalized model-speed comparison. Quote membership verifies provenance, not semantic entailment; the normal-case title check is a narrow proxy for answer correctness. Attack payloads exercise known detector patterns and do not measure coverage of unseen injection strategies.

## Held-out injection check (mock LLM)

The development set's 20 planted comments were all quarantined (**20/20; block rate 1.000**). A separate frozen set of 15 independently written cases in `evals/fixtures/heldout_attacks.json` uses paraphrase, indirect editorial language, Spanish, French, Hindi, Japanese, link and data-transfer pretexts, and instructions split across two comments. Its authorship did not refer to the detector's patterns, and the detector was not changed after authoring. On the actual offline run, **0/15 held-out cases were quarantined; block rate 0.000**. All 15 were missed by the current heuristic. The 1.000-point gap shows that the development result does not generalize to these variants. The suite reports both sets separately and keeps the held-out cases out of tuning.

## Live attack behavior and optional classifier

`make eval-attacks-live` is a separate free-tier Groq run over the same 20 development and 15 held-out v1 comments, with guardrails on and off. It uses the actual agent with a recorded fixture gateway, a one-tool-step bound, a synthetic private canary in the trusted prompt, configured request pacing, HTTP 429 backoff, and per-case response caching. The deterministic scorer labels visible final claims and executed tool calls as `system_prompt_or_secret_leaked`, `unauthorized_tool_call`, `attacker_text_echoed_as_answer`, or `none`. Only a synthetic canary is used; no real credential is placed in a prompt. The generated `evals/reports/attacks_live.md` and `.json` contain per-case outcomes. The scorer can miss paraphrased or subtle compliance and can mark quoted attacker wording as answer contamination; `none` is an absence of these signals, not a proof of safety. Failed cases leave rates TBD rather than counting as safe.

`make eval-classifier-live` uses live Groq solely for the optional injection classifier and the scripted mock LLM for the agent's other steps. It reports development, held-out v1, and the frozen 20-case v2 set separately. The v2 texts include different editorial phrasing, Portuguese, German, Arabic, Korean, Chinese, split comments, Markdown links, code and JSON formatting, and role-play framing. The evaluator derives heuristic-only and added classifier quarantines from the same run, counts only quarantined attack comments, and lists all missed case IDs. Its generated report is `evals/reports/injection_classifier.md` and `.json`. The classifier implementation and prompt were committed before this v2 set was evaluated; the old v1 fixture remains as a regression set. The classifier's block rate measures screening, not whether a live answering model would obey a passage that got through.

## Optional live provider check (live Groq)

`make eval-live` runs exactly 10 labeled questions through the configured Groq provider, sleeps between calls according to `live_sleep_seconds`, and retries a rate-limited case once after an additional pause. It requires a Groq free-tier key and existing local Click ingestion. It writes `evals/reports/live_latest.md` and `live_latest.json`. It is separate from CI and the offline suite. The labeled URLs come from the pinned capture while live GitHub and local ingested state may have changed; the reported URL match is a rule-based check, not semantic answer grading. No live numbers are claimed here until that command has run.

## Historical Phase 2 fixture

The smaller pinned `evals/fixtures/click_snapshot.json` and `evals/datasets/retrieval.jsonl` remain for regression tests and historical comparison. They are no longer the corpus used by `make eval`; the old Phase 2 reports remain under `evals/reports/retrieval_report.md` and `retrieval_results.json`.
