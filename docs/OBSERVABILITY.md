# Phase 7 observability

Each `repopulse ask` or `chat` question gets a 32-character `trace_id` in its answer. Events are appended to `traces/<trace_id>.jsonl` under the current working directory. This folder is ignored by Git. The JSONL format keeps the trace readable if a run stops on an error. A failed run records `run_error` with its exception type; the exception message is not copied to disk.

## Inspect and share a run

```sh
repopulse trace show RUN_ID
repopulse trace show RUN_ID --html traces/RUN_ID.html
```

The first command prints the complete event array as JSON. The second writes a standalone HTML page with search, event filtering, summary cards, and expandable event data. It embeds the trace; it does not load fonts, scripts, analytics, or data from the network. The [example viewer](trace_viewer_example.html) was generated by `python -m evals.render_trace_example` with a recorded Click issue and a mock LLM. The [README preview](trace_viewer_preview.png) was captured from that HTML in a browser.

## Event contract

Every event has a UTC `timestamp`, `run_id`, and `event` name. The event stream records:

| Event | Key fields |
| --- | --- |
| `run_start`, `run_end`, `run_error` | Question, repository, provider, budgets; completion or error type. |
| `memory_read`, `memory_write` | Session turns and selected SQLite memories; session write; explicit long-term add/forget, or a marker that `ask` made no long-term write. |
| `llm_call`, `plan`, `tool_selection`, `decision` | Model stage, status and latency; subquestions, chosen tool, and control-flow decision. |
| `tool_call`, `tool_retry` | Every attempt's tool name, arguments, step, result summary or error type, latency, and retry delay. |
| `evidence`, `quarantine` | Retrieved evidence ID, URL, type, title and excerpt; whether accepted, duplicate, or quarantined, and detector reasons. |
| `guardrail`, `claim_rejection`, `validation_failure`, `degradation` | Validation and redaction decisions, unsupported claim details, failed structured model output, and fallback reasons. |
| `token_usage`, `final_answer` | Character-based budget units, provider-reported prompt/completion tokens, and the validated answer. |

`tool_call` summarizes the returned evidence with IDs and URLs; individual `evidence` events carry the displayed passages. `llm_call` records prompt and completion lengths, latency, model name, and usage without storing successful prompt text or successful model output. Failed structured output is stored in `validation_failure` for diagnosis. Provider token counts are zero when the mock or provider gives no usage; `budget_units_used` is the agent's character-based reservation or provider usage, whichever is larger. It is not an exact tokenizer count.

## Local-data limits

The writer recursively applies the output redactor to event strings before writing. The viewer escapes embedded JSON and inserts event text with DOM `textContent` so retrieved markup is displayed as data. These are best-effort protections: the pattern redactor cannot identify every possible secret or private fact, and retrieved excerpts, user questions, memory records, rejected claims, and failed model output can still contain sensitive information. Keep `traces/` and exported HTML private when using private data, and delete files you no longer need. There is no automatic retention period or telemetry upload.
